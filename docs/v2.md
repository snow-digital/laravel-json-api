# JSON:API v2

v1 (`SnowDigital\JsonApi\ApiController`, `Resources\JsonApiResource`) nests every loaded relation
inside `attributes`, so a parent shared by many rows is copied into each of them. v2 serializes
spec-shaped documents instead, on top of Laravel's own
`Illuminate\Http\Resources\JsonApi\JsonApiResource` (Laravel 12.59+):

- `type`, `id`, `attributes`, `relationships`;
- `included`, deduplicated by `type:id` across the whole page;
- nested includes (`include=offers.entry`);
- sparse fieldsets per type (`fields[providers]=name`).

v1 is unchanged; both can be served side by side.

## Classes

| Class | Role |
|---|---|
| `SnowDigital\JsonApi\V2\JsonApiResource` | One model as a resource object. |
| `SnowDigital\JsonApi\V2\JsonApiCollection` | A page of them (Spatie `jsonPaginate()` gives `links` + `meta`). |
| `SnowDigital\JsonApi\V2\ApiController` | `index` and `show` for registered resources. |
| `SnowDigital\JsonApi\V2\Schema` | Model → `type`, and each type's declared relationships. |

## Routes

Resources are registered exactly as for v1 (`JsonApi::setResources()`, with `[class, only]`).
v2 has no auto-routing: declare the routes you want.

```php
use SnowDigital\JsonApi\V2\ApiController;

Route::prefix('api/v2')->name('api:v2:')->group(function () {
    Route::get('{resource}', [ApiController::class, 'index'])
        ->whereIn('resource', ['offers', 'providers'])
        ->name('browse');
    Route::get('{resource}/{id}', [ApiController::class, 'show'])
        ->whereIn('resource', ['offers', 'providers'])
        ->name('show');
});
```

The controller reads `resource` (and `id`) from the route on every call, so a fixed route works too:
`Route::get('offers', [ApiController::class, 'index'])->defaults('resource', 'offers')`.

`index` fires the same `AfterIndex` event as v1 (its `collection` is now typed `ResourceCollection`),
so listeners such as `meta=attributes` keep working.

To change the resource or collection class (e.g. to add cache headers), extend the controller:

```php
class CachedApiController extends \SnowDigital\JsonApi\V2\ApiController
{
    protected string $resourceClass = CachedResource::class;
    protected string $collectionClass = CachedCollection::class;
}
```

## Types

`type` is, in order:

1. the key given with `Schema::types([Offer::class => 'offers'])`;
2. the key a model class is registered under directly (`JsonApi::setResource('ratings', Rating::class)`);
3. the key of the resource the v2 controller is serving (remembered for its model);
4. the morph alias, verbatim (`offers.entry-mobile`);
5. Laravel's default, the model's class basename in snake case, plural.

**Register the types of models served through a query builder.** A builder's model is only known
once it is constructed, and constructing one reads and validates the current request (and may
have side effects), so v2 never constructs a builder other than the one it is serving:

```php
Schema::types([
    Offer::class => 'offers',
    Provider::class => 'providers',
]);
```

Without this, a provider included in `/offers` would fall back to its morph alias.

## Relationships

A type declares the relationships its builder allows as includes (`getIncludes()`, top-level names:
`offers.entry` declares `offers`). For builders other than the one being served, `getIncludes()` is
called on an instance that was never constructed, with only `$resource` set: it must not depend
on anything else the constructor does.

- **belongsTo and morphTo always carry an identifier**, even without `include`. It is read from the
  foreign key (and the morph type column), with no load and no query. A null key gives `data: null`.
- Their columns (`provider_id`, `entry_id`, `entry_type`) are removed from `attributes`.
- hasMany, belongsToMany and morphMany appear only when included.
- `id` is removed from `attributes`; it is the resource object's `id`. An attribute called `type`
  is kept (offers have one), although the spec reserves the name.
- A belongsTo whose owner key is not the related primary key gets an identifier only when loaded.

Included models are serialized with `V2\JsonApiResource`; override `relatedResourceClass()` to
change that per relation.

Includes follow the requested paths only:

- An included resource does not pull in relations that merely happen to be loaded on it (Laravel's
  default), e.g. a `parent` eager loaded through a model's `$with`.
- A resource in `data` is never repeated in `included`, even when a path reaches it again
  (`entry.parent`).
- The controller keeps only the include paths the query builder allows, the ones Spatie eager
  loaded. Laravel would otherwise lazy load the others row by row when invalid includes are
  configured not to throw. A custom endpoint serializing its own query should eager load what it
  lets clients include.

## Sparse fieldsets

`fields[type]=a,b` filters `attributes` of that type, in `data` and `included`. Identifiers stay.

v2 hides `fields` from Spatie's query builder: Spatie turns them into a SQL `select` per *table*,
which drops the primary and foreign keys that eager loads and identifiers need, and rejects fields
of related tables. In v2 the SQL always selects every column and only the serializer applies
sparse fieldsets. Unknown fields are ignored rather than rejected.

## A custom resource

Extend the resource to serialize something the generic controller does not serve:

```php
class OfferResultResource extends \SnowDigital\JsonApi\V2\JsonApiResource
{
    public function toAttributes(Request $request): array
    {
        return [
            ...parent::toAttributes($request),
            'availability_mobile' => $this->resource->availability_mobile,
        ];
    }
}

return OfferResultResource::collection($paginator); // a V2\JsonApiCollection
```

The type, identifiers and FK removal still come from `Schema`, so register the model's type.
